# Tinfoil GPU runtime evidence

These source and report observations support the GPU part of the [public-build serving contract](tinfoil-public-profile.md): one Hopper GPU in SPT mode, or up to eight Blackwell GPUs in MPT mode. [Local NVIDIA appraisal](../packages/tinfoil/src/worker-appraisal.ts).

## GPU mode and reference appraisal

The CPU-authenticated live report sampled on 2026-10-07 contains Hopper SPDM opaque-data version 1, feature flag `0` and protected-PCIe status byte `55`. This step parsed the exact CPU-bound bytes but did not repeat GPU signature verification. The NVIDIA appraisal separately verifies signature, nonce, device chain, signed driver/VBIOS RIMs, measurement matches and fresh OCSP for every GPU before releasing endpoint keys. [Raw-byte binding](../tools/tinfoil-public-build/main.go), [appraisal](../packages/tinfoil/src/worker-appraisal.ts).

NVIDIA's [Python mode parser](https://github.com/NVIDIA/nvtrust/blob/858ada9a17f58c482f578414ea2455498fa51e17/guest_tools/gpu_verifiers/local_gpu_verifier/src/verifier/attestation/spdm_msrt_resp_msg.py#L365) maps `0 → SPT`, `1 → MPT`, `2 → PPCIE`. The inspected [C++ header](https://github.com/NVIDIA/attestation-sdk/blob/9d12801cea8a198ea0f29640dfaf8a4017c841c5/nv-attestation-sdk-cpp/include/nv_attestation/gpu/evidence.h#L98) reverses SPT and MPT. Its [claim serializer](https://github.com/NVIDIA/attestation-sdk/blob/9d12801cea8a198ea0f29640dfaf8a4017c841c5/nv-attestation-sdk-cpp/src/gpu/claims.cpp#L194) omits the mode property. A client cannot infer the mode from its JSON success verdict. The appraisal reads each report's bytes after NVIDIA verifies them and requires opaque-data version 1 and the mode for the CVM's GPU count, using the Python interpretation: SPT for one GPU, MPT for several. Missing, malformed, duplicate or unknown fields reject, as do PPCIe and mixed modes. The parser alone performs no signature verification. [Mode parser](../packages/tinfoil/src/gpu-mode.ts), [mode policy](../packages/tinfoil/src/gpu-policy.ts).

Fresh eight-GPU reports from the DeepSeek (B200, `GB100`) and GLM-5.3 (B300, `GB110`) workers on 2026-10-07 carried mode `1` (MPT) in every report, with eight distinct device identities. NVIDIA's verifier accepted all of them with signed references and good OCSP responses. No conclusion depends on interpreting status byte `55` alone.

NVIDIA's [R595 GA notes, page 10](https://docs.nvidia.com/595trd1-trusted-computing-solutions-release-notes.pdf) state that devtools GPUs fail attestation. The [Python troubleshooting guide](https://docs.nvidia.com/attestation/advanced-documentation/latest/attestation-troubleshooting-guide/attestation_troubleshooting_guide_python_sdk.html) connects devtools to a mismatch with golden RIM measurements. The [C++ verifier](https://github.com/NVIDIA/attestation-sdk/blob/9d12801cea8a198ea0f29640dfaf8a4017c841c5/nv-attestation-sdk-cpp/src/gpu/verify.cpp#L370) derives `dbgstat=disabled` and `secboot=true` from matching those references. This relies on NVIDIA's measurement/reference contract; those properties are not separate direct mode queries in the serialized result. A devtools negative has not been exercised on a remotely controlled GPU.

The [manufacturer compatibility matrix](https://www.nvidia.com/en-us/data-center/solutions/confidential-computing/secure-ai-compatibility-matrix/) is populated by [NVIDIA's v0.08 data module](https://www.nvidia.com/content/dam/en-zz/Solutions/data-center/solutions/confidential-computing/compatibility-matrix/secure-ai-compatibility-matrix-v0.08.js). The complete downloaded array has 5,144 rows. Filtering the sampled VBIOS `96.00.D9.00.02` and driver `595.71.05` yields two released HGX H200 / PG520 SKU 280 rows: SPT and PPCIe. Compatibility therefore does not identify the actual mode. This table was research evidence, not a runtime root or an automatically trusted policy download.

## Driver execution and failure paths

The guest builds NVIDIA open kernel modules for `595.71.05` from [source commit 51edebe](https://github.com/NVIDIA/open-gpu-kernel-modules/tree/51edebee79919b54f498c19a0be31982cd97646e), with the [measured guest build recipe](https://github.com/tinfoilsh/cvmimage/blob/a4dbce07f5b0efbee1df678026db538eba66a613/nix/nvidia-modules.nix). The paths below are shared across architectures. Hopper and Blackwell differ in their [architecture-specific confidential-computing](https://github.com/NVIDIA/open-gpu-kernel-modules/tree/51edebee79919b54f498c19a0be31982cd97646e/src/nvidia/src/kernel/gpu/conf_compute/arch) and [SPDM certificate](https://github.com/NVIDIA/open-gpu-kernel-modules/tree/51edebee79919b54f498c19a0be31982cd97646e/src/nvidia/src/kernel/gpu/spdm/arch) files; the Blackwell-specific and NVLink-encryption paths were not traced and rest on NVIDIA's contract. Checked paths include:

- [Driver initialization](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/51edebee79919b54f498c19a0be31982cd97646e/src/nvidia/src/kernel/gpu/conf_compute/conf_compute.c#L137) rejects a non-CC/non-protected-PCIe GPU when the OS is confidential. SPDM is enabled for the CC path; registry overrides can disable it, so their absence matters. The guest's [fixed module parameters](https://github.com/tinfoilsh/cvmimage/blob/a4dbce07f5b0efbee1df678026db538eba66a613/tinfoil/internal/nvidia/modules.go#L18) contain no such override, and [module loading is locked](https://github.com/tinfoilsh/cvmimage/blob/a4dbce07f5b0efbee1df678026db538eba66a613/tinfoil/internal/pid1/hardening/module_lock.go).
- [SPDM initialization](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/51edebee79919b54f498c19a0be31982cd97646e/src/nvidia/src/kernel/gpu/spdm/spdm.c#L590) checks connection attributes and the responder certificate before starting the secured session. [Session-key derivation](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/51edebee79919b54f498c19a0be31982cd97646e/src/nvidia/src/kernel/gpu/conf_compute/conf_compute.c#L343) uses its export secret for encrypted channels.
- [UVM initialization](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/51edebee79919b54f498c19a0be31982cd97646e/kernel-open/nvidia-uvm/uvm_global.c#L121) obtains confidential-computing enablement from RM. Its [CPU–GPU copy path](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/51edebee79919b54f498c19a0be31982cd97646e/kernel-open/nvidia-uvm/uvm_conf_computing.c#L852) encrypts staged transfers and authenticates returned data. This is one checked driver path, not an inventory of every CUDA/engine transfer.
- [Fatal-session handling](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/51edebee79919b54f498c19a0be31982cd97646e/src/nvidia/src/kernel/gpu/conf_compute/conf_compute.c#L665) clears readiness, records fatal failure and tears down SPDM and session keys. The [ready-state API](https://github.com/NVIDIA/open-gpu-kernel-modules/blob/51edebee79919b54f498c19a0be31982cd97646e/src/nvidia/src/kernel/gpu/conf_compute/conf_compute_api.c#L185) rejects re-enabling after fatal failure. This narrows the failure-path requirement; the accepted manufacturer/publisher contract supplies reset, memory-scrubbing and engine/firmware behavior beyond these checked paths.

These mechanisms require both the authenticated guest driver and NVIDIA's authenticated device/firmware. Neither an unsigned readiness endpoint nor an overall GPU verdict establishes the actual serving channel by itself. [Manufacturer protected-transfer description](https://docs.nvidia.com/nvidia-secure-ai-with-blackwell-and-hopper-gpus-whitepaper.pdf).

## Remaining implementation

Fresh CPU/NVIDIA appraisal passed with the SPT guard enabled and sent no inference. The strengthened route also passed the full actual Pi completion/tool/reasoning/RPC-cancellation suite and a separate cancellation after a live text delta. All 43 provider tests and compiled/isolated package loader checks passed. [Pi harness](../scripts/live-pi.ts). The evidence CLI rejects malformed mode fields, and the native provider preserves a terminal mode rejection without retrying. Synthetic mode fixtures test field interpretation and the multi-GPU rules; signed MPT reports have since been accepted live, while a signed PPCIe device has not been exercised. [Multi-GPU policy tests](../tests/gpu-appraisal.test.ts). The real-evidence probe now also changes only the mode field in an otherwise authentic report and requires NVIDIA result `508` (`NVAT_RC_GPU_EVIDENCE_INVALID_SIGNATURE`), before any client mode guard. That negative passed alongside signature and nonce substitutions with zero inference requests. This tests signed-field coverage on Hopper evidence. [CLI tests](../tests/gpu-mode.test.ts), [native rejection test](../tests/provider.test.ts), [real NVIDIA negatives](../scripts/check-nvidia-verifier.ts). The [serving contract](tinfoil-public-profile.md) records the manufacturer/publisher channel/reset assumptions. GPU appraisal is connected to the owned public-build session.
