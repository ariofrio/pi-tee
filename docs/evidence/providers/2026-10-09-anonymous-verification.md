# Provider ratings verification under pi-tee revision 5

Verified 2026-10-09, with anonymous probes and repository-head observations saved alongside this report.

Cocoon's unclear cells resolve to **A3/H3**. Its ordinary two-hop RA-TLS path gives the attested proxy access to bodies; its CPU quote binds the certificate key, without a client challenge. The prior OpenPCC A2 claim, and the Chutes and Prem H1 claims, remain unproved at their stated strength. Their conservative admission values are A3 or H3 pending the evidence specified below. These are verification gaps, not demonstrated production regressions.

## How to read the table

**C** means confirmed at the stated scope; **D** means the old cell is replaced by the displayed new value; **U** means unresolved, with the old claim and conservative value both shown. A conservative value is the value to admit under “verified only”; it does not assert that the corresponding worst behavior was observed. Every cell links to evidence, including the model rule for forced values. All nonbaseline X3 values follow from A below A1; they do not assert that a provider actually stores bodies. Likewise H3 forces G3.

The controlling definitions are [verified only and weakest plaintext component](https://github.com/ariofrio/pi-tee/blob/fa5e1547d4a99a8f40b0279f08aa24f9bcaa03b9/docs/security-model.md), [A1–A3](https://github.com/ariofrio/pi-tee/blob/fa5e1547d4a99a8f40b0279f08aa24f9bcaa03b9/docs/security-model.md), [H1–H3](https://github.com/ariofrio/pi-tee/blob/fa5e1547d4a99a8f40b0279f08aa24f9bcaa03b9/docs/security-model.md), [G1–G3](https://github.com/ariofrio/pi-tee/blob/fa5e1547d4a99a8f40b0279f08aa24f9bcaa03b9/docs/security-model.md), and [X1–X3](https://github.com/ariofrio/pi-tee/blob/fa5e1547d4a99a8f40b0279f08aa24f9bcaa03b9/docs/security-model.md). Unpinned *data-only weights* do not by themselves make A3. A mutable executable, configuration that changes the plaintext-processing code, or unverified key custody can. Source behavior is identified below as **source only** unless the live evidence or client admission authenticates that source.

These are prospective adapter ratings except for pi-tee's existing Tinfoil direct baseline. The table evaluates the strongest specified client-verifiable path, not whether each vendor's stock SDK automatically performs all these checks. A public head is an observation of available source, not proof of the source or configuration deployed in production.

## Live evidence and connection binding

Every attestation probe used a newly generated random 32-byte challenge, hex or base64 encoded for the interface. Tinfoil's interface uses the challenge in its document transcript; Maple places the 64 ASCII hex bytes in its Nitro nonce. Each `.request.json` saves the URL, time, challenge and response status; each `.body` saves the exact response. No credentials, registration, inference requests, vendor messages or paid protocol operations were used.

Intel quotes were cryptographically checked locally using `dcap-qvl` **0.6.6** and collateral obtained directly from **Intel PCS**, rather than a vendor verdict. The saved population contains **25 quotes: 23 UpToDate and two OutOfDate** (Venice's NEAR worker and compose-manager). All 25 have module SVN at least `03 01 02`, TD attributes `0000001000000000`, and signed collateral `tcbEvaluationDataNumber = 20`, matching the current [pi-tee TDX floor](https://github.com/ariofrio/pi-tee/blob/e279fef3bf6f4539784ca9fcff249b037a4d9e32/packages/tinfoil/src/public-policy.ts#L15-L28). These floor checks do not turn an OutOfDate quote into H1. This investigation did not independently cryptographically appraise the live SNP or NVIDIA documents. GPU list length, echoed nonce and vendor `verified` fields are not accepted as G1/G2 evidence. Scripts: binding checks (private verification receipt), Intel verification (private verification receipt), unauthenticated mode-field decoder (private verification receipt); results are in the provider folders.

## Provider evidence and unresolved-cell settlements

### Tinfoil direct

**Client-verified design:** [public-build.ts](https://github.com/ariofrio/pi-tee/blob/e279fef3bf6f4539784ca9fcff249b037a4d9e32/packages/tinfoil/src/public-build.ts#L132-L193) authenticates release artifacts, the public source/configuration, guest endorsements, kernel/initrd and runtime chain. The [model-pack roots](https://github.com/ariofrio/pi-tee/blob/e279fef3bf6f4539784ca9fcff249b037a4d9e32/tools/tinfoil-public-build/runtime.go#L189-L206) and [restricted engine flags/endpoints](https://github.com/ariofrio/pi-tee/blob/e279fef3bf6f4539784ca9fcff249b037a4d9e32/tools/tinfoil-public-build/runtime.go#L255-L316) close executable model/runtime inputs, including rejection of remote code. The [authority policy](https://github.com/ariofrio/pi-tee/blob/e279fef3bf6f4539784ca9fcff249b037a4d9e32/packages/tinfoil/src/public-policy.ts#L30-L54) names public GitHub release workflows, Sigstore authority, runtime contract and transport. The publisher's [release workflow](https://github.com/tinfoilsh/confidential-deepseek-v4-1-flash/blob/c195341d2352c174220f85ebdfc8e4146c22e0e7/.github/workflows/tinfoil-release-publish.yml#L19-L40) is public; client acceptance verifies the corresponding logged endorsements, rather than accepting an arbitrary repository signature.

A1/H1/G1/X2 are **confirmed for admitted workers only**. Public code and guest/runtime checks support per-boot private keys, immutable roots and metadata-only API-key authentication egress; [software/transport contract](https://github.com/ariofrio/pi-tee/blob/e279fef3bf6f4539784ca9fcff249b037a4d9e32/packages/tinfoil/src/public-policy.ts#L47-L55) makes that contract explicit. Unadmitted or outdated workers do not inherit the baseline. Live probes support nonce/key/GPU-document binding but are not a fresh execution of the entire pi-tee public-build/GPU verifier. Model data authenticity is additional integrity protection, not the definition of A1.

### Privatemode

**Client checks:** [GetAttestedMeshCA](https://github.com/edgelesssys/privatemode-public/blob/753fa3fe1f2321c71743dda54f2ebbb160f89e14/internal/oss/attest/attest.go#L43-L85) generates its own nonce, validates Coordinator evidence, requires exactly one manifest and compares its bytes with the expected manifest. [ValidateAttestation](https://github.com/edgelesssys/contrast/blob/47dcc23be9c0e27b37909e86d8a0a0661e8ff428/sdk/verify.go#L141-L198) warns that the caller must check manifest content. This supports **A2 in pinned-manifest mode**: the Coordinator's measured policy constrains admitted pod code. Automatic CDN acceptance is a different authority policy and must not silently inherit the same fixed fingerprint guarantee.

**Current observation:** the public production manifest is **byte-for-byte unchanged** from the 2026-10-08 artifact, SHA-256 `384a2137e534357d74392bf3940373ff49d309d91551376b5a7f828e372af42b` (comparison (private verification receipt)). Its last-modified header is 2026-10-02. ## Out-of-scope rows and the broad group

- **io.net:** current primary docs offer attestation and optional CPU evidence, but the documented request flow submits ordinary JSON to a gateway. A GPU verdict and signed response do not prove that gateway cannot read the request. The unauthenticated attestation-only probe returned 403. The bounded conclusion is that this **documented public flow** lacks a client-verified protected plaintext closure, not that no io.net enclave can attest ([verification guide](https://io.net/docs/guides/confidential-inference/verification-guide.md), [quick start](https://io.net/docs/guides/confidential-inference/quick-start.md)).
- **NanoGPT:** the vendor explicitly includes possible plaintext at gateway/proxy layers outside the enclave in its [verification boundary](https://docs.nano-gpt.com/api-reference/tee-verification.md). The credential-free attestation probe returned 401. An upstream GPU check or echoed challenge does not attest that plaintext gateway. Out of scope for that documented route.
- **Maple:** the current public monorepo now supplies primary backend source, replacing the survey's dependence on teep. Its unauthenticated attestation handler asks AWS NSM for a nonce/public-key document ([Nitro handler](https://github.com/MaplePrivacyLabs/Maple/blob/de44a301cc693f932ce8f864df7412247452ed5d/services/opensecret/src/web/attestation_routes.rs#L69-L94)); the live response is a real decoded Nitro document with our challenge. The [client proxy handshake](https://github.com/opensecretcloud/maple-proxy/blob/6b1a66c3db9e84a42fbb33690015193d8c8daeb5/src/proxy.rs#L222-L226) authenticates the OpenSecret hop. Even if the backend verifies Tinfoil/Privatemode internally, the client has a **Nitro plaintext hop**, with no defined pi-tee TDX/SNP host floor for it. Do not describe this as absent attestation.
- **OpenGradient:** the pinned [primary gateway architecture](https://github.com/OpenGradient/tee-gateway/blob/ee26d285899973734af07b93ac62b0abe0fe35b4/README.md#L5-L22) describes a Nitro gateway routing to external OpenAI/Anthropic/Gemini services. Nitro gateway attestation does not protect plaintext inside those inference services. No public client-fresh TDX/SNP inference closure was established.
- **“Hyperscalers, Apple, Google, others”: still unresolved as a universal claim.** It does not name an enumerable route set. The current [Azure portfolio](https://learn.microsoft.com/en-us/azure/confidential-computing/overview-azure-products) lists Whisper confidential inferencing and confidential GPU VMs; that is bounded product evidence, not proof that no other API exists. Google's downloaded current technical brief (private verification receipt) describes hardened TPUs, a key provisioned after internal attestation, and Android/Pixel clients verifying that key; independent client-side verification of attestation evidence is listed as future work (PDF pp. 14–15). [Anthropic’s paper introduction](https://www.anthropic.com/research/confidential-inference-trusted-vms) expressly describes research rather than a delivered interface.  Apple's [PCC hardware design](https://security.apple.com/documentation/private-cloud-compute/hardwarerootoftrust) and [release transparency](https://security.apple.com/documentation/private-cloud-compute/releasetransparency) are actual primary evidence, so lack of a third-party chat API must not be confused with lack of attestation or public releases. AWS's [Mantle zero-operator-access design](https://aws.amazon.com/blogs/machine-learning/exploring-the-zero-operator-access-design-of-mantle/) describes controls, not a demonstrated pi-tee client CPU/GPU evidence path. The original broad absence claim cannot be confirmed for every unspecified cloud product. **Settlement:** replace the group with named product/API routes, then test each published challenge/key/evidence interface and plaintext closure. Until that exists, do not turn a bounded survey into proof that no such API exists anywhere.
